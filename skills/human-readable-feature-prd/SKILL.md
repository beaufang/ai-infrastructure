# 面向研发团队的功能需求文档

## 目标

将已有产品资料整理为一份**给人看的、可直接用于研发评审和开发的功能需求文档**。

主要读者包括：产品、前端、后端、测试、设计，以及其他需要在开发前理解功能行为的相关人员。

本 Skill 与“实现规格”“编码计划”“面向 Coding Agent 的 Spec”有明确区别：

- 重点解释**用户如何使用、业务如何运转、系统应该表现成什么样**。
- 清晰呈现用户流程、交互规则、业务规则、状态、异常和验收条件。
- 技术方案只作为理解约束和边界的输入，不作为文档主线。
- 除非某个技术细节会直接影响用户可见行为，否则不要把文档写成接口、数据库表、类、文件或开发任务清单。

最终文档应当能够直接用于需求评审：一名刚接触该需求的前端、后端或测试人员，在没有额外口头讲解的情况下，也能理解主要流程、关键规则和验收方式，并据此开始工作。

## 输入材料

优先使用用户已经提供或项目中已经存在的资料，典型输入包括：

- 产品原型、线框图、页面截图、Figma 导出图或界面说明
- 技术方案、架构设计文档
- 现有需求说明、会议纪要、工单、旧版 PRD 片段
- 现网行为、历史规则、兼容逻辑
- 业务规则、角色权限、字段字典、接口文档
- 用户明确给出的决定、修正和约束

不要求所有材料都齐全。

用户已经提供过的信息、当前请求中引用的项目文件，都视为已知上下文。不要要求用户重复提供。

如果能够读取项目文件，应先检查与当前功能相关的资料，再开始生成文档。只读取还原需求所需的最小范围，避免无关信息干扰。

### 信息可信度优先级

当不同资料互相冲突时，按以下优先级处理，并显式暴露冲突，不要静默选择：

1. 用户 / 产品负责人明确给出的最新决定或修正
2. 已确认的产品原型或正式需求
3. 已确认的业务规则和领域文档
4. 技术方案中的约束、集成边界和已确认决策
5. 为兼容性而参考的现有实现或现网行为
6. 根据材料做出的合理推断

第 6 级信息绝不能当作已确认事实表述。

## 核心原则

### 1. 人的理解优先

文档应优先适配人类阅读，而不是 Agent 解析。

默认阅读顺序应当是：

**这是什么 → 谁会使用 → 主流程怎么走 → 每个关键交互如何表现 → 哪些业务规则决定行为 → 出错时怎么办 → 怎样算完成。**

### 2. 以原型和用户旅程作为交互主线

存在产品原型时，应围绕真实用户路径、页面、弹窗、控件和状态组织详细需求。

对每个关键页面或交互，尽量说明：

- 用户从哪里进入
- 用户在这里想完成什么
- 用户能看到什么、操作什么
- 每个有意义的操作之后发生什么
- 什么条件会改变展示、可用状态、文案、结果或跳转
- 适用时补充：加载、空数据、成功、失败、禁用、过期、无权限、重试等状态

不要把原型上的文字机械转录成需求文档。

### 3. 业务行为与技术实现分离

功能需求文档负责说明：

- 用户可见行为
- 业务规则
- 决策逻辑
- 状态转换
- 角色与权限
- 错误和异常行为
- 验收标准

技术方案负责说明：

- 内部架构
- 服务拆分
- 数据库结构
- 类 / 函数 / 文件结构
- 底层协议和具体实现方式

只有当技术细节会改变产品行为、限制需求，或者是跨团队理解所必需时，才写进需求文档。否则引用技术方案，不重复复制。

### 4. 不确定性必须显式标记

严禁为了“文档看起来完整”而自行补全未知规则。

统一使用以下标记：

- **[待确认]**：产品或业务尚未决定，或者现有资料存在冲突
- **[推断]**：根据已有资料可以合理推断，但尚未得到明确确认
- **[技术约束]**：产品行为受到技术方案限制

如果未知项会影响范围、权限、金额、不可逆操作、主流程或核心业务结果，应视为阻塞问题，在最终确认该部分之前提出简洁问题。

如果未知项不阻塞主体文档，则继续生成，并统一收集到“待确认事项”。

### 5. 复杂分支优先图形化

只有当图能显著降低理解成本时才使用图。

优先使用：

- Mermaid `flowchart`：端到端用户流程 / 业务流程
- Mermaid `stateDiagram-v2`：生命周期 / 状态转换
- Mermaid `sequenceDiagram`：多角色、多系统或异步交互难以仅靠流程图说明时

不要为了形式感把三步直线流程也画成图。

### 6. 需求必须可验证

避免使用“友好”“合理”“快速”“正常”“智能”“尽量”“适当”等不可验证词语，除非同时给出可观察标准。

对重要行为，至少说明：

- 前置条件
- 触发行为
- 系统预期行为
- 最终状态 / 用户可见结果
- 必要时说明失败行为

对于包含条件、分支、状态转换、权限或异常的关键行为，使用“前提 / 当 / 那么”形式编写验收标准。

## 工作流程

### 第 1 步：确认交付上下文

明确：

- 当前要描述的功能或改动
- 主要阅读者
- 如有必要，区分现状与目标状态
- 本期范围和明确不做的内容
- 当前可用的输入资料

如果这些信息已经清楚，不要重新做一遍产品发现或从零访谈。

### 第 2 步：读取并整理来源资料

在正式写文档前，先在内部形成一个简洁的信息映射：

| 来源 | 能确认什么 | 状态 |
|---|---|---|
| 产品原型 | 页面、入口、用户可见交互 | 已确认 / 草稿 |
| 技术方案 | 技术约束、集成边界 | 已确认 / 草稿 |
| 需求说明 | 业务目标、规则 | 已确认 / 不完整 |

同时记录冲突和缺失信息。

除非团队需要追溯来源，否则不必把这张内部分析表直接输出到最终需求文档。

### 第 3 步：还原端到端用户旅程

识别：

- 用户角色 / 参与者
- 入口
- 前置条件
- 正常主流程
- 重要分支
- 终态结果
- 跨页面或跨角色衔接

如果流程存在分支，或跨多个步骤 / 页面，生成一张简洁主流程图。

流程图必须使用**业务语言**，不要用服务名、类名或具体实现方式作为主要节点。

### 第 4 步：建立行为清单

针对每个有意义的页面、模块、弹窗或业务步骤，识别：

- 用户操作
- 前置条件 / 展示条件
- 页面或系统响应
- 业务判断规则
- 状态变化
- 权限
- 校验
- 成功结果
- 失败 / 超时 / 重试行为
- 必要的后续影响

优先把相关行为组合成一个完整业务任务，不要把每个按钮点击都拆成孤立需求。

### 第 5 步：主动检查遗漏与冲突

主动寻找前端、后端和测试在评审时最可能追问的问题。

适用时至少检查：

- 首次操作 / 再次操作
- 重复提交，以及用户侧的重复操作表现
- 返回上一页 / 页面刷新 / 再次进入
- 加载过程 / 长耗时操作
- 空数据
- 部分成功
- 超时
- 重试
- 并发修改 / 陈旧状态
- 权限变化
- 无效 / 过期数据
- 历史数据兼容
- 取消 / 撤销
- 不可逆操作
- 跨设备 / 跨会话
- 外部依赖失败
- 边界值
- 不同角色差异

禁止自行发明规则。无法确定时标记 **[待确认]**。

### 第 6 步：按“人类优先”结构生成文档

默认使用 `template.md` 的结构，并根据实际需求裁剪。

不要因为模板里存在某个章节，就强行输出空章节。

推荐阅读顺序：

1. 需求概述
2. 范围、角色与场景
3. 端到端业务 / 用户流程
4. 页面与交互行为
5. 业务规则和状态转换
6. 异常与边界场景
7. 影响行为的数据 / 字段 / 权限
8. 验收标准
9. 待确认事项
10. 产品原型和技术方案等参考资料

### 第 7 步：生成验收标准

验收标准是产品意图和测试验证之间的桥梁。

使用两种层级：

**功能级验收清单**：用于快速确认功能完整性。

**“前提 / 当 / 那么”场景**：用于描述包含条件、状态变化、权限、错误或重要边界的行为。

示例：

```text
AC-03 — 处理中重复提交
前提：上一笔操作仍处于处理中
当：用户再次发起相同操作
那么：系统不得创建第二笔业务操作
并且：页面继续展示当前操作状态
```

不要把整份需求文档变成数百条测试场景。需求文档只保留代表性、关键验收条件；穷举测试用例属于测试计划。

### 第 8 步：只在有价值时增加需求追踪

对于中大型功能，可以增加简洁追踪表，把核心需求与页面和验收标准关联起来：

| 需求 | 原型 / 页面 | 关键业务规则 | 验收标准 |
|---|---|---|---|
| FR-01 | 订单详情 | 只有满足条件的订单展示退款入口 | AC-01、AC-02 |

除非用户明确要求，否则不要把开发任务 ID、代码文件或类加入此表。

### 第 9 步：执行“可开发性检查”

输出前确认，一名新加入的前端、后端或测试人员能否回答：

1. 谁能使用这个功能？
2. 流程从哪里开始、在哪里结束？
3. 正常路径是什么？
4. 重要分支有哪些？
5. 每个关键交互具体做什么？
6. 哪些业务规则决定系统行为？
7. 有哪些状态，状态如何变化？
8. 失败、超时、空数据、重复操作时会发生什么？
9. 哪些内容明确不在本期范围？
10. 产品和测试如何判断功能已经完成？

如果某个问题无法回答，是因为现有资料没有定义，则加入 **[待确认]**，不要伪造答案。

## 输出规则

### 语言

默认使用中文。技术名词如 API、SDK、HTTP、WebSocket、Token 等，如果翻译后反而降低团队理解效率，可以保留通用英文写法。

### 写作方式

- 面向跨职能需求评审会议，不面向 Coding Agent。
- 先给结论和流程，再展开细节。
- 优先描述可观察行为，不写抽象口号。
- 术语与产品原型和业务领域保持一致。
- 优先使用短段落、表格和必要图示降低阅读成本。
- 只有当解释“为什么”有助于避免误解时，才补充规则背景。
- 同一规则不要在多个章节完整重复，应通过编号交叉引用。

### 需求编号

文档较大、需要引用时使用编号：

- `FR-xx`：功能需求 / 可观察行为
- `BR-xx`：业务规则
- `AC-xx`：验收标准
- `Q-xx`：待确认问题

小功能不必为了形式强制编号。

### 产品原型处理

当存在截图或原型图片时：

- 按页面名 / 图号引用。
- 输出格式支持图片时，把需求说明放在对应原型附近。
- 重点补充静态原型无法表达的动态行为：跳转、条件、状态、异常、权限和后果。
- 不要仅凭视觉样式推断原型中没有表达的隐藏逻辑。

### 技术方案处理

只提炼会影响产品行为的技术约束，例如：

- 操作结果异步返回，因此页面必须存在“处理中”状态。
- 外部服务可能延迟返回最终结果，因此需要定义等待和超时表现。
- 某业务操作确认后不可逆，因此交互必须提供明确二次确认。

然后引用技术方案查看实现细节。

除非用户明确要求，否则不要把 API 定义、数据库结构、代码结构或架构正文复制进需求文档。

## 质量标准

一份高质量需求文档应当满足：

- **易读**：新加入的前端、后端、测试无需口头讲解即可理解主要功能。
- **流程清晰**：先看到端到端用户 / 业务流程，再进入局部细节。
- **无歧义**：规则描述条件和结果，而不是形容词。
- **足以开发**：重要状态、异常、权限和边界均有定义或明确标记待确认。
- **诚实暴露缺口**：未知内容明确标记，不伪装成事实。
- **不重复技术方案**：需求文档关注业务与交互，技术实现另有归属。
- **可测试**：测试人员能够直接从文档推导正常、分支、异常和边界场景。
- **可维护**：章节围绕产品概念和用户流程组织，不依赖容易变化的代码结构。

## 常见问题

### 问题：把技术方案重新抄一遍

错误做法：文档一半都是 API、数据库表、服务拓扑和代码约束。

正确做法：只说明这些技术事实对产品行为造成的影响，并引用技术方案。

### 问题：把原型转录成文字

错误做法：“页面有标题、按钮 A、按钮 B、列表 C。”

正确做法：说明每个控件什么时候出现、什么时候可用、触发什么行为、操作后状态怎么变化，以及异常情况下怎么处理。

### 问题：只描述正常流程

错误做法：主流程很完整，但超时、重试、重复操作、权限变化和数据过期全部没有定义。

正确做法：系统检查边界场景，未定义内容统一标记 **[待确认]**。

### 问题：按按钮拆碎需求

错误做法：每次点击都变成一条孤立需求，导致读者看不到端到端业务过程。

正确做法：以用户旅程和业务任务作为主结构，在其中说明具体交互。

### 问题：AI 自动补齐空白

错误做法：为了让文档完整，默默把缺失决策写成确定规则。

正确做法：明确区分已确认行为、推断、技术约束和待确认事项。

### 问题：把需求文档写成测试计划

错误做法：几百条测试用例占据主体，研发反而难以理解需求。

正确做法：需求文档保留关键验收标准，完整测试用例由测试计划承载。

## 配套文件

- `template.md`：默认中文功能需求文档模板
- `example.md`：中文示例

本 Skill 采用常见的软件需求实践：以用户旅程组织需求、明确范围和非目标、描述可观察行为、显式暴露不确定性，并使用结构化验收标准连接产品、研发与测试。
