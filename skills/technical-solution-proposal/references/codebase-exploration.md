# 代码库探索指南

## 1. 目标

代码库探索用于确认：

- 系统现在实际上如何运行；
- 核心调用链、状态和数据边界；
- 各模块真正拥有的职责；
- 外部副作用和隔离边界；
- 已有能力能否复用；
- 改造影响、成本和风险。

探索必须由方案问题驱动，不是无目标遍历仓库。

## 2. 何时需要

以下情况通常需要：

- 存量系统改造；
- 需要判断职责应放在哪个服务；
- 需要确认已有能力；
- 方案涉及状态、事务、一致性、隔离、重试或副作用；
- 需要评估复用、迁移和改造成本；
- 用户描述可能与实现不一致。

绿地概念方案或通用外部文章可不探索，但应说明哪些判断未经内部实现验证。

## 3. 探索计划

每项探索先写清：

| 字段 | 说明 |
|---|---|
| 探索问题 | 要确认什么 |
| 初步假设 | 当前认为可能是什么 |
| 证据入口 | 文档、模块、类、配置、测试或日志 |
| 决策影响 | 结果会影响哪个方案判断 |
| 停止条件 | 获得什么证据后停止 |

示例：

```text
探索问题：
评估执行应落在 server 还是 proxy？

需要确认：
Agent 构建、Skill 装载、会话状态和工具解析目前由谁负责。

决策影响：
判断是否能够复用生产执行语义，以及是否会产生双实现。
```

## 4. 探索深度

### 轻量

检查：

- README 和已有架构文档；
- 构建文件和模块结构；
- 启动入口；
- 核心配置；
- 外部依赖。

适合确认系统边界。

### 标准

继续检查：

- 业务或任务入口；
- 核心调用链；
- 状态保存位置；
- 数据读写；
- 消息流；
- 外部调用；
- 扩展点与 Hook；
- 异常、重试和降级；
- 关键测试。

适合整体技术方案。

### 深度

仅在可能改变总体路线时检查：

- 并发和线程模型；
- 事务与一致性；
- 缓存和会话生命周期；
- 配置版本行为；
- 权限和数据边界；
- 部署拓扑；
- 历史提交和架构演化；
- 性能和事故证据。

## 5. 推荐顺序

```text
项目文档
→ 构建与模块结构
→ 启动入口
→ 用户请求或任务入口
→ 核心调用链
→ 状态与数据
→ 外部调用和副作用
→ 扩展机制
→ 异常与降级
→ 测试和运行证据
```

不要从 DTO、工具类或数据库表开始理解系统。

## 6. 核心问题

### 系统如何运行

- 请求从哪里进入；
- 经过哪些关键组件；
- 状态由谁维护；
- 结果如何产生；
- 同步和异步边界在哪里。

### 职责在哪里

- 谁拥有业务状态；
- 谁拥有执行能力；
- 谁拥有配置；
- 谁拥有数据和审计；
- 是否存在职责重复。

### 副作用在哪里

- 哪些工具访问真实业务；
- 哪些 Hook 写生产数据；
- 哪些消息触发下游；
- 哪些调用不能安全重放。

### 能力能否复用

- 会话隔离；
- 调度与任务；
- 配置快照；
- 权限与审计；
- Trace 与证据采集；
- 测试执行入口。

### 改造影响是什么

- 修改哪些系统边界；
- 是否需要新服务；
- 是否影响生产链路；
- 是否需要数据迁移；
- 是否增加运维复杂度。

## 7. 代码证据卡

```text
事实：
MAIN Agent 在 proxy 中完成构建和执行。

证据：
模块、文件、核心类、方法或配置入口。

方案含义：
若要求复用真实执行语义，评估执行应优先进入 proxy 边界。

置信度：
高 / 中 / 低。

待确认：
是否存在代码之外的部署或组织约束。
```

正文只保留有决定意义的事实。完整路径进入调查记录或附录。

## 8. 停止条件

满足以下条件后停止：

- 核心调用链已确认；
- 主要职责边界已确认；
- 决定路线的约束已确认；
- 外部副作用边界已确认；
- 候选路线的主要影响可以判断；
- 继续阅读只会增加实现细节，不会改变总体方案。

关键问题无法由代码回答时，回到用户沟通。
