# 用户沟通指南

## 1. 目标

用户沟通用于确认代码和外部资料无法回答的内容：

- 为什么要做；
- 当前问题的真实影响；
- 哪些结果代表成功；
- 谁需要作出决定；
- 存在哪些业务、资源、历史和组织约束；
- 用户当前倾向和不可接受的代价。

用户不是单纯的信息提供者，而是方案共创者。

## 2. 沟通原则

- 每轮最多提出三个高价值问题；
- 优先询问会改变问题定义、方案路线或首期范围的信息；
- 能从材料和代码确认的问题，不重复询问；
- 普通实现细节不逐项确认；
- 使用具体场景，不用空泛问题；
- 明确区分用户确认事实、用户判断和工作假设。

## 3. 首轮问题

根据上下文选择，不机械全部询问。

### 决策

- 这份方案最终需要谁确认什么？
- 评审通过后，下一步会发生什么？
- 当前最有争议的决策是什么？

### 现状

- 现在没有这套能力时，团队具体怎么做？
- 最近一次典型失败是什么？
- 哪个环节最消耗时间或最容易出错？

### 影响

- 问题造成了什么业务、质量、效率或风险影响？
- 哪个影响最需要优先解决？
- 为什么必须现在处理？

### 约束

- 哪些系统、流程或职责明确不能改变？
- 首期时间、资源和上线边界是什么？
- 是否存在代码之外的历史或组织原因？

### 成功

- 首期完成后，什么现象会证明方向有效？
- 哪个指标最有说服力？
- 什么结果意味着应该停止或调整？

## 4. 三个检查点

### 问题确认

回传：

- 当前现状；
- 一到三个核心问题；
- 初步根因；
- 影响；
- 待确认事项。

确认问题：

> 我们真正要解决的是不是这个问题？

### 路线确认

回传：

- 主要候选路线；
- 推荐方案；
- 决定性理由；
- 主动接受的代价；
- 首期闭环。

确认问题：

> 这条路线和范围是否符合现实约束？

### 成品确认

确认：

- 受众和篇幅；
- 核心结论；
- 敏感信息；
- 需要读者做出的决定；
- 是否需要拆分详细设计。

## 5. 沟通记录

使用以下分类：

| 类型 | 说明 |
|---|---|
| 已确认事实 | 用户明确确认或有可靠材料 |
| 用户判断 | 用户对问题或方案的解释 |
| 工作假设 | 暂时采用以继续推演 |
| 待确认问题 | 可能改变方案路线 |
| 非关键未知 | 暂不影响总体方案 |

## 6. 何时必须回到用户

出现以下情况时必须回传：

- 代码事实与用户描述不一致；
- 外部研究推翻了原始方案假设；
- 新发现改变问题定义；
- 候选路线在组织或资源上可能不可行；
- 首期范围需要明显扩大或缩小；
- 关键业务指标无法定义；
- 对外发布可能涉及敏感信息。

不因普通字段、类名或实现细节中断用户。
