# 整体技术方案结构

## 1. 写作顺序

实际推演顺序：

```text
问题 → 根因 → 核心判断 → 机制 → 场景 → 架构 → 取舍 → 实施 → 验证
```

最终文档可以结论前置，但不得跳过推演。

## 2. 技术评审版默认结构

### 1. 方案结论

回答：

- 当前最重要的问题；
- 推荐路线；
- 决定性理由；
- 首期范围；
- 需要确认的决策。

控制在一页内。

### 2. 现状与核心问题

说明：

- 当前怎么做；
- 一到三个具体问题；
- 问题影响；
- 为什么现在处理。

### 3. 根因与关键约束

说明：

- 问题产生机制；
- 结构性根因；
- 核心矛盾；
- 业务、技术、资源和组织约束；
- 事实、判断和假设。

### 4. 核心设计思路

用三到五个机制解释方案如何解决问题。

每个机制回答：

```text
通过什么机制
→ 改变什么行为
→ 解决哪个问题
→ 如何验证
```

### 5. 关键场景与运行机制

至少一个端到端场景：

- 场景目标；
- 当前失败点；
- 新方案过程；
- 信息、状态和控制变化；
- 成功证据；
- 异常和降级。

### 6. 总体架构与职责边界

按以下顺序：

1. 系统边界；
2. 能力分层；
3. 核心组件；
4. 组件职责与非职责；
5. 数据流和控制流；
6. 外部依赖；
7. 隔离与失败边界。

### 7. 候选方案与取舍

说明：

- 主要路线；
- 比较维度；
- 推荐方案；
- 主动接受的代价；
- 不适用条件；
- 重审条件。

### 8. 首期范围与实施路径

区分：

- 首期必须；
- 首期可选；
- 后续增强；
- 明确不做。

阶段按验证目标划分：

```text
验证核心机制
→ 覆盖主要场景
→ 建立治理闭环
→ 规模化与自动化
```

### 9. 指标、风险与待确认事项

指标形成：

```text
问题 → 机制 → 行为变化 → 指标 → 价值
```

风险说明触发条件、影响、应对和回退。

### 10. 评审决策

使用可确认或否决的表述，例如：

- 是否认可总体技术路线；
- 是否认可系统责任边界；
- 是否认可首期最小闭环；
- 是否接受推荐方案的主要代价；
- 哪些后续能力不进入首期。

## 3. 正文与附录

### 正文保留

- 问题和根因；
- 核心判断；
- 解决机制；
- 关键场景；
- 总体架构；
- 重大取舍；
- 首期范围；
- 验证指标；
- 风险和决策。

### 默认下沉

- 完整领域模型；
- 数据库表和字段；
- 完整 JSON Schema；
- Kafka 消息字段；
- 接口和 DTO；
- 全量状态枚举；
- Mock 匹配细节；
- 完整指标和告警；
- 单元测试清单；
- 权限矩阵；
- 数据保留策略。

当某项细节直接决定总体路线时，正文只保留相关部分。

## 4. 表达约束

- 每章开头先给判断；
- 结论前置；
- 不使用技术名词替代逻辑；
- 不使用功能清单替代运行机制；
- 不用“提升效率、增强稳定性”替代因果解释；
- 不重复相同边界；
- 不隐藏不确定性；
- 不把未来所有可能性放进首期；
- 不虚构数据和收益。

## 5. 图的使用

正文通常只需要：

1. 问题或现状图；
2. 核心机制或关键场景图；
3. 总体架构图；
4. 必要时的阶段路线图。

每张图前后必须解释：

- 这张图想回答什么；
- 读者应该关注什么；
- 它支持哪个判断。

图不能替代文字论证。
