# Agent 与 Skill 离线评估整体技术方案（精简示例）

## 1. 方案结论

当前 Agent 和 Skill 的验证方式无法同时保证真实性、可复现性和安全性。只检查最终回答看不到 Skill、工具和多轮行为；直接运行生产 Agent 又可能访问真实业务并受动态配置影响。

建议建立一个独立的离线评估闭环：

> 冻结评测输入和被测配置，在隔离环境中运行真实 Agent 决策核心，以严格 Mock 替代业务工具，采集完整轨迹，并通过规则裁判和语义裁判形成质量结论。

首期只建设评测集发布、配置快照、隔离执行、严格 Mock、轨迹采集、双裁判和结果查看。基线比较、自动 Trace 回流和发布门禁不进入首期。

本次评审需要确认总体路线、控制面与执行面的职责边界，以及首期范围。

## 2. 现状与核心问题

### 2.1 当前方式

Agent 或 Skill 调整后，团队主要依赖人工试问、最终回答检查或分散的测试逻辑。

### 2.2 三个核心问题

**结果不可信。** 最终回答可能正确，但 Skill 选择、工具参数、调用顺序或多轮状态已经错误。

**过程不可复现。** Prompt、Skill、模型、知识和裁判持续变化，历史结果难以解释和重跑。

**执行不安全。** 真实 Agent 可能调用生产工具、写入业务数据或污染生产会话和 Trace。

## 3. 根因与关键约束

根因是当前没有一个独立评估运行边界，也没有同时冻结输入、被测配置、外部环境和裁判规则。

方案必须同时满足：

- 尽可能复用生产 Agent 的真实决策语义；
- 不访问真实业务，不产生生产副作用；
- 一次评估可以重现和审计；
- 能检查最终回答之外的行为轨迹；
- 首期不新增独立服务。

因此，不能重新实现一套测试 Agent，也不能仅进行文本评分。

## 4. 核心设计思路

### 4.1 冻结评测条件

发布后冻结评测场景、Mock、断言、被测 Agent 配置和裁判规则，使历史运行可以解释和重跑。

### 4.2 真实决策核心，仿真外部环境

真实运行 MAIN Agent、Skill、ReAct 和必要的 SUB Agent；API、METHOD 和知识检索全部切换为严格 Mock。

### 4.3 完整轨迹作为证据

保存每轮回答、Skill 加载、工具调用、SUB Agent 路径、时延和 Token 等可观察行为，不保存内部 Chain-of-Thought。

### 4.4 规则与语义双裁判

工具名、参数、次数、顺序和禁止调用由确定性规则判断；正确性、忠实性、指令遵循和多轮一致性由固定 LLM 裁判判断。硬约束不能被语义高分抵消。

## 5. 关键场景

以“第二轮补充运单号”为例：

1. 用户第一轮询问快件位置；
2. Agent 应加载查件 Skill，但因缺少运单号不能调用查询工具；
3. 用户第二轮补充运单号；
4. Agent 调用 `query_parcel`；
5. 工具不访问真实业务，而是返回评测集冻结的 Mock 结果；
6. Agent 根据结果回答当前位置；
7. 规则裁判检查 Skill、工具参数和调用顺序；
8. LLM 裁判检查回答是否正确、忠实并保持多轮一致；
9. 系统保存本次运行的配置、轨迹和裁判结果。

这个场景体现了方案的核心：Agent 决策是真实的，外部环境是可控的，评估条件是冻结的。

## 6. 总体架构

### 控制面

放在管理侧系统，负责：

- 评测集和裁判配置；
- 被测配置快照；
- 运行调度；
- 结果、审计和权限；
- 首期基础结果页面。

### 执行面

放在现有 Agent 执行侧，负责：

- 构建真实 MAIN Agent；
- 隔离评估会话；
- 替换业务工具和生产 Hook；
- 运行多轮场景；
- 采集轨迹；
- 执行规则和语义裁判。

### 基础设施

- 数据库保存定义、快照、任务和结果；
- Kafka 异步派发场景任务；
- Redis 保存短期隔离会话；
- 现有共享 API 承载执行包和结果契约。

控制面拥有评估状态，执行面拥有 Agent 运行语义，双方不重复实现 Agent。

## 7. 候选方案与取舍

### 方案 A：在管理侧重建测试 Agent

优势：管理和执行集中。  
缺点：复制生产执行逻辑，容易产生语义漂移，维护两套 Agent。

### 方案 B：管理侧控制，现有执行侧运行真实 Agent

优势：复用真实执行语义，系统职责较清晰。  
缺点：需要跨模块调度和严格隔离生产副作用。

### 方案 C：直接回放生产 Trace

优势：场景真实。  
缺点：数据治理、可复现性和副作用处理复杂，难以作为首期基础。

**推荐方案 B。**

决定性理由是：本方案最重要的目标是验证真实 Agent 行为，同时隔离外部副作用。方案 B 能保留生产执行语义，且不需要新增一套 Agent 实现。

主动接受的代价是：评估需要跨模块调度，并在执行侧建立工具、会话和 Hook 的隔离机制。

## 8. 首期范围与实施路径

### 首期必须

1. 不可变评测集；
2. 候选 Agent 配置快照；
3. 隔离多轮执行；
4. 严格业务工具 Mock；
5. 回答和工具轨迹采集；
6. 规则与单一 LLM 裁判；
7. 场景结果查看。

### 首期不做

- 自动生产 Trace 回流；
- 多裁判投票；
- 强制发布门禁；
- 完整配置版本平台；
- 复杂基线管理；
- 完整人工复核工作流；
- 高并发运行。

### 阶段

**阶段一：验证核心机制。**  
完成一个 MAIN Agent、一个多轮场景和一个工具 Mock 的端到端闭环。

**阶段二：覆盖主要行为。**  
扩展 Skill、工具审批和必要 SUB Agent 场景。

**阶段三：建立治理。**  
补充多试次、基线比较、人工复核、权限和审计。

**阶段四：规模化。**  
增加 Trace 回流、自动聚类、资源治理和发布门禁。

## 9. 验证指标

### 结果可信度

- 硬约束能够稳定识别错误工具行为；
- LLM 裁判与人工标注达到约定一致性；
- 同一冻结条件下重跑结果可解释。

### 安全隔离

- 真实业务工具调用为零；
- 生产会话和 Trace 写入为零；
- 评估数据可独立清理。

### 工程可用性

- 调整 Prompt 或 Skill 后可以发起回归；
- 单个失败场景能够看到完整证据；
- 评估失败能够区分质量失败和技术失败。

## 10. 风险与评审决策

主要风险：

- Mock 维护成本可能较高；
- LLM 裁判存在漂移和偏差；
- 执行侧资源可能影响线上 Agent；
- SUB Agent 和动态 Skill 会增加快照复杂度。

本次需要确认：

1. 是否认可“真实决策核心 + 仿真外部环境”；
2. 是否认可管理侧控制、执行侧运行；
3. 首期是否只支持 MAIN Agent；
4. SUB Agent 是否必须进入首期；
5. 是否接受基线比较和人工复核后置。
